## Microservices Patterns (ISBN: 978-1-61-729454-9)

Chapter 10: Testing microservices: Part 2

- Integration tests verify if application interacts properly with its dependencies (infrastructure and other
  applications).
- A good strategy for testing communication with infrastructure is testing adapters only, with maybe supporting classes.
  Docker containers (test containers) may be helpful for deploying required infrastructure.
- A good strategy for testing communication with external services is to prepare contract tests.
- Consumer-side contract tests simulate a provider and check if the application can communicate with it.
- Provider-side contract tests simulate a consumer and check if the application can communicate with it.
- To run HTTP adapter consumer-driven contract tests, external service is mocked with HTTP stub.
- To run asynchronous communication consumer-side contract test, the message is generated and the test checks if it was
  correctly handled by the event handler. To run asynchronous communication provider-side contract test, adapter is
  triggered to publish a message and the test verifies if the message is correct.
- To test sagas, consumer-side contract tests check if the message is correctly generated by the adapter and if it can
  correctly interpret the reply. Saga provider-side contract tests verify if the message was correctly handled and if
  the correct message was sent back.
- Component tests are acceptance tests for a single service. It should be tested from an API perspective in isolation
  with its dependencies stubbed.
- Component tests are business-oriented, they should focus on the behavior of a service from client's perspective, not
  on the internal implementation.
- The service can be run in-process, in the same virtual machine (faster to run, easier to write, but not testing the
  service in conditions similar to real deployment); or out-of-process (more complex to write and run, but the
  conditions of real deployment are better simulated).
- Infrastructure can be stubbed with in-memory implementations. External services can be stubbed using contracts, or
  mocked from a test itself, e.g. using WireMock.
- Component tests are slower to run, they should be placed in a separate source sets and run with a separate command.
- End-to-end tests verify if multiple services work correctly with each other.
- Multiple services, or the entire application, need to be deployed to run end-to-end tests. As a result, they are slow
  and should be minimalized.
- Instead of focusing on separate functionalities, entire user journeys should be tested (entity created, updated,
  deleted etc. in a single test case).
- To make e2e tests understandable for the business, they should be described using a human-readable DSL.
