# Readings

## Designing Data-Intensive Applications, 2nd Edition (ISBN: 978-1-09-811902-7)

Chapter 1: Trade-Offs in Data Systems Architecture

- Compute-intensive applications are optimized for efficient computation processing, handling parallel computation.
  Data-intensive applications focus on data processing, ensuring consistency, accessibility of large volumes of
  information.
- Except backend engineers there are two roles interested in data: **business analysts**, who generate reports about the
  activities of organization to help management making better decisions, and **data scientists**, who search for
  insights in data, often using machine learning, to plan next business features based on customers activities.
- **Data engineers** are responsible for integrating operational and analytical systems, **Analytics engineers** are
  responsible for transforming the data to make it more useful for business analysts and data scientists.
- While OLTP systems are usually accessed using pick queries and data modifications (by ID), OLAP systems are usually
  accessed using long-running, resource-heavy aggregate queries. Also, OLTP databases usually don't handle custom
  queries (queries are defined in application code), OLAP databases usually face custom-created queries generated by
  data engineers or BI tools.
- Data warehouses contain copy of data from all application databases within the ecosystem in relational form. They are
  optimized for business analysis to not impact the operational data stores.
- Data lakes also contain copy of data from all application databases, but in a raw form (like AVRO files, images etc.).
- They are optimized for machine learning.
- Data is copied from primary to secondary data stores using ETL processes (Extract, Transform, Load).
- The part of a system, which is a core competency of an organization, or where the organization has competitive
  advantage, should be managed in-house. Anything else should be outsourced to external vendors.
- Cost of maintaining infrastructure in-house depends on the competency and workload of the team.
- One of disadvantages of cloud infrastructure is that providers rarely agree to deliver any customizations to the
  system.
- Systems kept in-house are less efficient when the load has peak-characteristic, when for most of the time the system
  burns resources.
- Systems which involve communication between their components over a network are called **distributed systems**. Each
  component taking part in a distributed system is called a **node**.
- Different parts of the system should have their own databases, mostly not to impact the performance of each other.
- Microservices provide a technical solution to people problem: different teams can work independently on different
  parts of the system. In small organizations microservices provide more overhead than profit and are not recommended.
- Architecture of a system should not only address technical needs, but also people needs (according to GDPR, users
  should have a right to be forgotten).
- Automated systems help make decisions impacting people (like granting a loan, being hired for a job etc.).
  Engineers should feel socially-responsible for their system and ethics.
- There are multiple unsolved challenges related to law compliance: how to ensure data erasure in a database, which
  operates on immutable log files? Currently, there are no general recommendations regarding the technical stack
  addressing some problems.
- Data is stored because organizations believe that the value of storing it is greater than cost. However, the risk of
  compromising the data should also be part of cost-benefit calculation.
- Even in a secure environment, there are always governments or police forces, which could demand access to
  organizations' data. This should be kept into consideration, as even a geolocation data positioning users close to the
  abortion clinic can make them a potential suspect in countries, where abortion is illegal.
- The decision what data to store and what data not to store should be a balance between potential profits of storing
  all possible information speculatively (big data approach) and data minimalization. Some data is not worth storing.
